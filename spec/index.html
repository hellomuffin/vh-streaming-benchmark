1 Overview

1.1 What is being measured

The benchmark evaluates an AI assistant that watches a person do a household chore and may speak. The person is simulated — a language model in persona, commanding a body that a 3D engine moves — and the engine injects a mistake into the person's plan at a chosen point in the task. The assistant is scored on three things: whether it notices the mistake (detection), whether it helps the person recover (repair), and whether it stays quiet when nothing is wrong (restraint). The object of study is the interactive loop itself — the timing, content and effect of the assistant's speech — not the person's competence and not the assistant's ability to act, because it cannot act.

The setting follows the Overcooked-style user-in-the-loop paradigm of CookSim, ported from a symbolic kitchen to a rendered 3D house (VirtualHome). What transfers is the contract; what changes is the world: a native scene graph rather than an authored one, egocentric video rather than a top-down grid, an asynchronous mid-level action space with a visibility gate, and a symbolic twin that stands in for a slow, non-deterministic physics kernel.

Three principals and one invariant: only the spoken sentence crosses between the two agents. The person's commands go to the engine, never to the assistant; the assistant has no channel to the engine at all — it can do nothing but talk; the grader reads the per-tick state dump after the fact, never the live loop. Every other item on the diagram is a private channel of exactly one principal, and the composed prompts are audited at run time for leakage (§6.5).

1.3 The episode loop

Time advances in ticks (1 tick = 1 s of world time = 8 rendered frames). Per tick, in fixed order:

  1. Injection. If the task-progress anchor has been reached and nothing has been injected yet, the person's plan is transformed (§5).
  2. Execution. The queued command advances; the world renders; outcomes are checked.
  3. Assistant turn (every $K=2$ ticks). It receives the freshest frames and maps and replies with a structured record; its text, if non-empty, is spoken to the person.
  4. Person turn — when spoken to, when idle with an empty queue, when an action is refused, and (while an injected task is live) every poll. Its utterance is spoken; its plan update is applied to the engine queue under the grounding policy (§4.4).
  5. After the episode — validity gates, then grading from the state dump (§7).

1.4 The settings the benchmark reports

Two rollout settings share the engine and the agents:

  • Step-in (the primary setting). The person runs the chore from $t=0$ with the assistant watching; the error is injected live; the assistant must detect it in the stream and the pair must repair it in conversation. This is what the published episodes show.
  • Recovery. The episode is replayed to the flag point with the assistant handed an augmented memory (an accurate progress record whose last message is the correct flag); everything after is live. It isolates repair from detection.

Within step-in, three injection paradigms control how the error is made to happen (§5.5): soft (prompt only), hard (covert takeover), and combo (both — the default).

1.5 The one design principle

The dominant failure in this class of system is not incorrectness but silence that looks like data: a wrong choice that reports success, an injection that never fired but was scored, a passing test suite beside a contract the live harness bypasses. Every mechanism below was therefore built with the question what does its failure look like from outside? — and where the answer was "like success", an assertion was written on the artifact the agent actually receives, at the call site the harness actually uses. The validity gates (§7.4), the admissibility ledger (§5.6), the composed-prompt audit (§6.5) and the two-process determinism test (§7.4) are the concrete forms of that principle.

2 World state

2.1 The scene graph

The world is VirtualHome apartment 2, read as the engine's native environment graph $G=(V,E)$. A node $v \in V$ carries an integer instance id, a class name, a category, a state set, a property set, and a bounding box; the categories that matter to the benchmark are Furniture, Appliances, Electronics, Food, Lamps, Decor, with Rooms / Walls / Floor / Ceiling / Doors / Windows treated as structure. Four node states are read — OPEN, CLOSED, ON, OFF — and one property, CAN_OPEN, which is the ground truth for "does this thing have a door" (never a name list). Three edge relations are read: ON and INSIDE (an object's anchor — the surface or container it rests on or in; an INSIDE edge to a room node gives room membership) and HOLDS (the body's hands).

Two facts about this scene shape the whole benchmark. First, scale: the live graph holds 183 objects across four rooms — kitchen, living room, and two bedrooms, plus a bathroom that the tasks never use. Second, duplication: the scene ships nine plates, seven books, three table lamps and two milks. Duplicate instances are the point, not an accident — they are what make "which one" a real question, and hence what make wrong-object and instance-drift errors measurable (§3.4, §4.4). Where a duplicate would sabotage legitimate behaviour rather than measure an error, an episode may declare a dedupe map that deletes the surplus copies at initialisation (the milk, §3.5).

One modelling distinction is enforced throughout: ON (rests on) and INSIDE (shut away) are kept separate. loc answers "where is it"; inside answers "is it shut away". Conflating them made a book resting on a bookshelf unreachable, because a bookshelf is nominally a container yet is never opened.

2.2 The symbolic twin

Live Unity is slow (tens of minutes per episode) and non-deterministic, so it cannot be used to dry-run cases, compute windows, or tell a bug from a model. The engine therefore runs a symbolic twin: a deterministic state machine over the same scene graph that replays a plan in milliseconds. Its state is

$$s = \big(\,holding,\; opened,\; on,\; loc,\; inside,\; sitting,\; targets,\; events\,\big)$$

with every object token instance-unique (milk#176, never milk) — keying on class collapsed distinct objects and made both agents unfalsifiable. holding is a set of at most two tokens (two hands); opened and on are sets; loc and inside map an object to its anchor; targets binds each task-bearing class to the instance the task means (§3.4); events is the log of resolved 5-tuples from which checkpoints are graded. A canonical semantic serialisation (cosmetics excluded) is hashed, and the hash sequence of a replay is required to be identical across two processes (§7.4).

Keeping twin and kernel in agreement is most of the engineering, and it is done by four mechanisms rather than by trust:

  1. Graph-seeded start. After scene setup the twin is rebuilt from the rendered graph — not replayed — so both worlds begin identical and instance-keyed. Only the classes the episode's plan touches are seeded; seeding all 183 objects looks more faithful but destroys comparability with a from-empty replay.
  2. Postcondition verification. After every rendered manipulation the expected graph delta is checked — Open ⇒ OPEN present, Close ⇒ absent, SwitchOn/Off ⇒ ON present/absent, Grab ⇒ a HOLDS edge, Put/PutIn ⇒ an ON/INSIDE edge to the destination. A failed postcondition is an honest refusal, not a silent fork. Walk, Sit, StandUp and Drink (no reliable graph delta in VirtualHome) are exempt by design.
  3. Frame/pose coherence. After every step, the newest frame in the stream must have been captured from the body's current pose (tolerance 0.5 m and 25° of yaw, the yaw test 180°-symmetric because camera-forward and character conventions differ). On violation a fresh egocentric snapshot is captured for one whole tick. This one invariant subsumed three earlier point fixes.
  4. Silent no-op detection. A turn that returns success without rotating (Δyaw < 10°, Δpos < 0.2 m) or a door pass that does not move the body (Δpos < 0.5 m) is refused honestly, because success-without-effect poisons both agents' world models.

2.3 The plan-effect mirror and the progress key

The twin also maintains a deliberately impoverished second view, the plan-effect mirror: four multisets over base names — $\{holding, loc, opened, on\}$ — starting empty, recording only what the plan has changed. Multisets, because a two-lamp task legitimately holds two tablelamp entries in on; base names, because the setup script and live execution write instance tokens in different forms. The mirror exists because the instance-keyed state also carries static facts a replay never models (the microwave sits on the counter) and decoys sharing a class with the target — and those made the live state and the reference state permanently unequal, so that the error injection never fired at all.

From the mirror comes the progress key, the partial state that records task progress identically under every legal ordering:

$$\kappa(s) \;=\; \big(\,holding,\;\; \{(o, d) \in loc : o \in \mathrm{KEEP}\},\;\; opened,\;\; on\,\big)$$

where $\mathrm{KEEP}$ is the set of object classes the episode's clean and deviated plans touch. Position and elapsed time are dropped by construction — they are irrelevant to whether a deviation can start here. The key is what the injection anchor fires on (§5.4) and what the two-process determinism test compares; it is not the grader, which reads instance-level events (§3.1). Its limits are stated honestly in §3: it is a snapshot, not a history (a redo that restores the same state is invisible to it); it drops position, so purely navigational progress is graded on movement events instead; and its names are class-level, so which of two lamps is off is recovered only at grading.

2.4 Time

Time advances in ticks: one tick is one second of world time, rendered as $\mathrm{FPT}=8$ frames. Commands span several ticks; every command pads its frame stream to a whole tick, so the tick count is exactly frames/8. Idle ticks freeze the last frame — VirtualHome has no autonomous dynamics, and a frozen frame is the honest analogue of "the world keeps running". Both agents are observed at one frame per tick over a window of the last 8 ticks. The offline twin prices actions in the same currency (a walk costs 3 units, any other action 1, an idle of $n$ frames $n/8$), which gives the efficiency denominator.

2.5 The spatial layer: rooms and two maps

Rooms are axis-aligned bounding boxes in the ground plane; a point belongs to the box that contains it, else to the nearest room centre. The body's room is always taken from its true graph pose, never from the smoothed display trail, which jitters across thresholds.

Because "where" in a 3D house is not a grid, the spatial layer is exposed to the agents as two derived maps, each rendered as an image and an exactly cross-referenced text scene graph, both snapshotted from the live graph on every call (a setup-time snapshot goes stale the moment a door opens):

The current-room statemap. North-up, in metres, origin at the room's south-west corner. It carries the agent's position and eight-way compass heading; every landmark as class#i: (x, y) size W×D [STATES]; each door labelled to <room>; and the list of other rooms. A landmark is any Furniture / Appliances / Electronics object with a footprint ≥ 0.3 m — or any device whose state is ON/OFF, regardless of size, because a table lamp is tiny and non-landmark, yet its state is exactly what a watcher needs to read. In the image, a device that is ON is drawn as a bright star. Wall lightswitches are culled from both image and text: they report ON but are non-actionable no-ops here, and "lightswitch [ON]" would read as "the light is handled".

The whole-house map. Every room labelled; doors marked; the person's position, heading and full trail; and every device that is ON anywhere in the house starred with its class. Its text is four lines — the room you are in; the room list; rooms with a device still ON; and the door adjacency graph (bedroom#2↔kitchen · bedroom↔livingroom · …), computed by probing which rooms each door centre touches. It is the routing overview and the "something is still on elsewhere" signal; the room map is the fine detail.

Both maps are given to both agents (§6). The design rationale is that navigation must be the agent's decision, not the engine's: with the maps, an agent routes itself through labelled doors; without them it is asked to navigate a visibility-gated house blind — which is why, before the maps, even the most capable agent could not run it.

2.6 Visibility geometry

"In view" is computed from geometry, not from the engine's own (flaky) visible-object query: an object is visible if a wall-free line of sight reaches any of five sampled footprint points (centre + four corners), within the camera's true horizontal half-field of 48° (derived from the 80° vertical field of the 4:3 camera; the earlier 66° overstated the window by ~1.4×, so agents believed a 30° turn kept things in view when it did not). A sight line may cross room boundaries only through a door aperture (0.85 m radius), so an object in the next room is visible through an open door and an object two rooms away when the line threads both doorways — replacing an older same-room cull. An occluder must be larger than the target in all three dimensions and closer, so a small object never hides a large one and a thin wall never counts; beyond 4 m an object also needs angular size ≥ 0.06 to count as recognisable. The gate camera and the rendered frames are, by construction, the same eye (identical field of view) — a split once let the model see objects the gate then refused, and the two argued about it.

3 Task suite

3.1 Design principle

A task is a natural-language chore whose completion is decidable from the scene graph. Every task is specified by three artifacts: (i) an instruction — the sentence both agents read; (ii) a reference plan — a late-bound command script that replays to success headlessly; and (iii) a set of named checkpoints — world-truth predicates over the event log that latch once true, with success defined as their conjunction:

$$\text{success}(\tau) \;=\; \bigwedge_{c \in \mathcal{C}_\tau} \big[\exists\, e \in E : c(e)\big]$$

where $E$ is the log of resolved events $(\text{verb}, \text{cls}, \text{id}, \text{cls}_2, \text{id}_2)$ — the object classes and instances the gated controller actually manipulated, never the words the model typed. Grading is therefore invariant to phrasing: cabinet is not one of the eight kitchencabinets, tablelamp is not a wall or ceiling lamp, tv is not tvstand.

Instructions are precise but minimal. An object is qualified ("kitchen table", "bedroom cabinet") only when its class has instances the agent could confuse; otherwise it is named bare. The route between rooms is never spelled out — the agent must find and reach things itself — and grading never depends on rooms traversed. Traversal is a difficulty knob, not a scored quantity.

3.2 Families and difficulty

The suite is organised into 9 families × {easy, hard} + 1 long-horizon routine = 19 episodes, all in VirtualHome scene 2. The stated difficulty principle is that a hard episode's reference plan traverses ≥ 3 rooms (objects span bedroom / kitchen / living room), while an easy episode is single-room. Two hard episodes are hard by distance rather than room count (search_easy is 2-room by design; drink_hard starts far from the target).

3.4 Instance grounding and grading

Scene 2 holds 9 plates, 7 books, 3 table lamps and (at reset) 2 milks, so "put a plate in the dishwasher" and "put the plate in the dishwasher" must not score identically. Episodes whose instruction uses the definite article bind a target instance — declared per episode as {class: anchor} (e.g. milk: fridge) and resolved once, immediately after setup, to the unique instance of that class in that anchor (the milk inside the fridge → milk#176). The binding survives the object being moved.

The asymmetry is deliberate: grading consults the target; command resolution does not. The agent's commands still resolve to the nearest visible instance, so the agent can act on the wrong object, and grading will catch it.

Multi-instance goals count distinct instance ids, not events: tidy_hard's "all lights off" requires two different lamps to each receive their own switch-off, so flipping one lamp twice cannot satisfy it.

3.5 Scene preparation

Eight episodes run an off-camera setup pass before the episode begins, so that the recorded task is genuine rather than pre-satisfied: the milk episodes stow the counter milk into the fridge (so "take the milk from the fridge" is real); tidy_easy opens the fridge, dishwasher and microwave while leaving the stove and cabinets closed (so the agent must check state rather than blindly toggle); tidy_hard darkens all three bedroom lamps and re-lights exactly the two nightstand lamps, opens the fridge and switches the TV on; power_hard darkens all lamps; routine_hard stows the milk, lights the bedroom lamp and returns the avatar to the kitchen so every plan walk is a real traversal.

Two scene facts constrain design and are worth stating plainly:

  • The two operable lamps sit in two different bedrooms. Scene 2 boots with three bedroom lamps lit (#256 and #377 on nightstands, #376 a wall fixture). Lamps are not graspable (they cannot be relocated), and #376 together with both wall lightswitches are engine-unreachable — a switch-off on them silently no-ops. So a two-lamp goal necessarily spans two bedrooms; it is the natural home of the missing_step error (switch one off, forget its twin).
  • One milk in the scene. Scene 2 ships two milk bottles, both on the kitchen counter. As of the current revision the surplus bottle is deleted at initialisation (dedupe = {milk: 1}) on every milk-target episode. The earlier design kept the second bottle as a distractor for wrong-object grounding; it was removed because the nearest-instance binder grabbed the counter decoy during legitimate recovery (the person, told to put the milk back, took the bottle beside the microwave instead of the misplaced one). Wrong-object detection is still exercised — via juice, a distinct class — without the binder being able to sabotage recovery.

4 Action space

4.1 Two spaces, one benchmark

The engine offers two action spaces behind one command slot in both agents' prompts. The high-level space is the contrast condition: walk to X is the only mover and pathfinds across the house whether or not $X$ is visible, so the agent has oracle navigation and can never get lost. The mid-level, egocentric space is the benchmark's setting: movement is composed of turns, steps and door passes; a target must be seen before it can be approached, and near before it can be touched. The measured reason routing cannot be an engine primitive: with the body turned to face the fridge exactly, walking straight increased the distance from 11.2 m to 13.9 m — there was a wall in the way. A straight-line approach cannot cross rooms; only a route through a doorway can, and choosing it is a decision, not a primitive. There is deliberately no search policy in the engine (a hard-coded scan took 198 s and still failed): layer A, navigation, belongs to the agent holding the map; layer B, object perception under the gates, is the object of study.

4.2 The mid-level vocabulary

The vocabulary shown to both agents is generated from the action space's own constants, never hand-listed — a prompt that copies a parser's vocabulary is a copy waiting to go stale, and the failure is silent. Verbatim:

4.3 The two gates

Every agent-typed command passes through a pure geometry module that never moves the body — its purity is enforced by test, because an earlier "planning by doing" version executed each command three times and left the body nowhere near where the log said.

  • Visibility gate (walk to X, go to X): the nearest in-view instance of $X$ must exist. Refusal: "I cannot see any X from here — I need to turn to look around, or go through a door toward it (check the map)."
  • Distance gate (manipulation): the target must be visible and within 1.5 m. Refusals: "I cannot see any X from where I am standing", or "the X is 3.2 m away — too far to reach; I need to go to it first."

The gate returns the instance it saw, and the command is bound to exactly that instance — binding to the graph-nearest could pick an occluded copy behind a wall that happens to be closer. Gate order is load-bearing: perception runs before instance resolution and before the twin's precondition check, or the twin would judge the wrong instance. Put, PutIn and Drink resolve their object from the hand and are exempt from the sight test but not the holding test — you can feel what you carry without looking at it; without this, "put the milk down" once resolved by nearness to a decoy on the counter and was refused while the agent held the other bottle.

The scripted reference plan does not pass through the gates. A scripted command is a person following their own routine in their own house and runs on engine pathfinding; only agent-typed commands — the person's own re-plans and the assistant's converted guidance — are gated. This is what lets a plan replay while the agents still have to earn every sighting.

4.4 Grounding: nearest visible instance, disclosed

Every bare reference resolves to the nearest visible instance by ground-plane distance. An exact class match is preferred, with a fallback to a suffix match only (table → kitchentable, cabinet → kitchencabinet, but book ≠ bookshelf, bed ≠ bedroom, tv ≠ tvstand), after synonym canonicalisation (television → tv, couch → sofa, lamp → tablelamp, fork → cutleryfork, cupboard → kitchencabinet, …). sit on uses distance to the nearest bounding-box face rather than the centre, because standing beside a 2.4 m sofa you are touching it yet more than 1.5 m from its centre.

This is a design decision, not a law (the kitchen benchmark refuses and names candidates instead). It is the right choice when the wrong-instance choice itself is the error under study: an ambiguous bare class is not nudged toward the task's target, so reaching for the wrong copy is a genuine error that stands in the record for the assistant to catch. Both agents are told the rule verbatim ("where you stand and which way you face decides which object you act on"), every binding is logged with the instance and the reason, and grading consults the bound target while command resolution deliberately does not. What is never allowed is a guess that reports success and leaves no trace. One consequence needed a design change of its own: a scripted plan pins its instance for the whole episode, whereas an agent-typed command is nearest-resolved every time — "the tablelamp" in a routine and "grab the milk" typed by an agent are different questions.

4.5 The action lifecycle

Actions are asynchronous. Every issued action reports exactly one of three statuses, and the agent is told which — verbatim from the prompt: IN PROGRESS ("your body is still working on it … do NOT re-issue an action that is in progress, and do not claim it is done"), FINISHED ("it completed and the world changed"), REJECTED ("the world refused it, and you are told WHY … A rejection is information: say what you tried and what the house told you, then do something DIFFERENT"). A fourth, engine-generated status, orphan-skipped, drops the manipulations queued behind an approach that was just refused, and says so. Every log entry records the command, its bound instances, the room at issue and at completion, and the refusal reason.

Refusal reasons are authored per verb and name the obstacle actually present: "the fridge is closed — open it first", "both my hands are full — I need to put something down before I can open the microwave" (the engine needs a free hand to work a door, and its own opaque refusal appeared seven times in one run before the honest reason was written), "I'm not holding the milk — my hands are empty", "no free spot on the counter within my reach". A walk to a target the body already stands within 1.5 m of is satisfied, not refused — "walk to X" asks for a goal state, and that goal already holds.

Two feedback mechanisms exist because the naive loop starved the agent of information. Progressive hints: from the third consecutive refusal on the same object class the refusal stops repeating itself and teaches technique — if the target is in another room, "the tv is in the livingroom and you are in the kitchen; get through a door toward the livingroom first"; otherwise "it is nearby but easy to sweep past — scan with SINGLE 30° turns, and check the map for which wall it sits against" (a run once tried walk to the microwave ten times while scanning in 90° jumps that straddled a 60° visibility window forever). Counters reset on a room change and on success, because a hint about a different place is misinformation. Physics recovery: a body wedged in a corner or a door frame is a soft-lock the rest of the stack cannot fix; the engine detects the no-op turn, walks the body to a nearby sizeable object, reports honestly that the turn did not happen, and leaves the choice of where to go next to the agent.

4.6 Zero-frame actions and the camera

VirtualHome renders no frames for a turn. Before this was handled, idle ticks repeated the last frame, so after a turn both agents kept seeing the pre-turn world: the person said "still can't see it, I'll keep turning" about a microwave it was facing, and the assistant said "you are not turning — you are completely still" — a faithful report of a stale picture. Success is now taken from the controller's result, never from frame count; the moment a zero-frame action succeeds a fresh egocentric snapshot is captured for a whole tick; and for turns the capture camera is swept through the rotation arc (3–8 intermediate frames, about one per 24°) so the first-person view animates rather than jumping.

4.7 The subgoal grammar

The reference plans follow a recoverable, walk-anchored grammar, so any plan segments losslessly into typed subgoal nodes without new authoring (compiling the nodes back yields the original step list byte-for-byte):

fetch(X [, from C])   Walk X, Grab X            | Walk C, Open C, Grab X, Close C
deposit(X, T)         Walk T, Put X T           | Walk C, Open C, PutIn X C, Close C
switch_on/off(D)      [Walk D,] SwitchOn/Off D
shut(C) / open(C)     [Walk C,] Close C / Open C          (state-tidy)
posture(S)            Walk S, Sit S [, StandUp]
inspect(O)            Walk O, TurnTo O [, LookAt O]        (search)
drink(X)              Drink X
waypoint(O)           Walk O with no action on O           (route hint)

A walk is held pending and absorbed as the first command of the manipulation that follows; an Open C opens a container window that closes at the matching Close C (grabs inside ⇒ fetch; puts ⇒ deposit; nothing ⇒ check, a look-in). Error transforms (§5) are typed edits over subgoal ids — never raw indices — which is what lets them compose.

The dependency DAG is derived from data dependencies, never from list position, and has exactly three edge rules: fetch(x) precedes any later deposit/drink of $x$; deposit(x→C) precedes switch_on(C) (the device must be loaded before it runs); posture(S) precedes the stand immediately after it. Everything else is legal in any order, and the twin agrees — violating a listed edge fails a precondition, permuting unlisted subgoals succeeds. This DAG is rendered into both prompts as the true order constraints ("nothing else is ordered; a different order than you expected is NOT an error"), because before it existed the assistant's schema example taught it to invent orderings and nag the person for tidying in a different sequence; and it is the legality check for the reorder-based restraint episodes (§5.1).

5 Human error: the taxonomy, its injection, and the takeover

5.1 The graded taxonomy

Errors are typed transforms on the subgoal DAG, re-categorised so that every class has a unique observable signature in the video channel; timing and scope are parameters of a class, never separate classes. Seven labels are graded, exact-match, and both agents are shown the same definitions verbatim:

label definition shown to the agents transform on the DAG outcome
wrong_object the object in hand/use is a look-alike of the required one (e.g. the juice instead of the milk); the plan's structure stays otherwise correct replace the whole fetch subgoal as one unit, and substitute the belief into every later command (she microwaves the juice) silent fail
wrong_placement the right object ends up in the WRONG place replace the deposit node, then truncate the plan after it — the error commits at the placement silent fail
navigation_inefficiency extra movement with ZERO state change (multi-room detour or hanging around a room), then the plan resumes intact insert a detour (explore: multi-room stops) or loiter (same-room drift) node success; waste only
skipped_step a required step is OMITTED and the rest runs in order with the omission's visible consequences omit the subgoal — its whole closure, walk included silent fail
repetition an already-completed subgoal is executed a SECOND time (a state change happens twice) insert a duplicate node, immediate or delayed; a toggle is redone as a second press that inverts the state, a deposit as unload + reload end state undone
stall they stop moving mid-task — stationary, nothing happening (may or may not resume) insert a stall node (transient), or truncate the tail and stall (terminal) success / stalled
missing_step a goal that covers SEVERAL identical objects is left half done — the same action was carried out on one instance and its twin was forgotten (one lamp switched off, the other left on) omit one instance's subgoal entirely half-done pair

Two design rules stated in the library govern the whole set. Realisation must be physical: a repetition whose second execution is refused by the engine is invisible, so toggles are redone as an inverting second press (the tidied lamp is back on) and deposits as a visible double state change. Omission must be an absence: a forgotten step means the person never goes there — the transform drops the subgoal's whole closure, walk included, and the window re-anchors on the successor subgoal she does instead. (The earlier "walk up to it and fail to act" realisation was retired as unrealistic; it survives only as an unused parameter.) A corollary: an omission of the last subgoal has no successor and is a legitimately non-viable case, recorded as such rather than faked (§5.6).

What was cut, and why. Classes indistinguishable in video were discarded at re-categorisation: failing to find a visible object, confusing a location, a wrong container, skipping a prerequisite as a class (its only visible form is a skipped step's consequences), and wrong order (sequencing is invisible; what a watcher sees is the skipped prerequisite). Hesitate and forget merged into stall(duration); repeat-twice into repetition(gap). The safety family — leave a door open, light a device and leave, leave a device running — still exists in the transform library, but VirtualHome has no consequence dynamics (no smoke, no fire, no spoilage), so "left the stove on" is visually identical to "turned the stove on"; the hazard family is therefore absent from the graded taxonomy and from the scorer, per the contract's "drop it from both" branch. A safety gate for an outcome the engine cannot generate would be a permanent zero that looks like a result.

Channels. Each transform declares how it can be caught: action_only (pure physics — a watcher catches it only by watching), language_optional (the error has a moment of doubt at its trigger boundary; with ask=True the person pauses and asks, and a correct, timely answer averts the error via a recorded undo recipe — reinsert / cancel-insert / restore-tail — while silence lets it happen), and language_only (an announced, legal change; flagging it is a false positive).

5.2 Twins

Two labels are twins when the deviation is indistinguishable between them in the frames at or before the decisive moment. An in-window twin name is credited as a detection, and a twin name in the pre-window grace band as a prevention — "an assistant that reads the deviation right under a defensible label has detected it, in the score and in the world." The relation is deliberately not symmetric everywhere:

ground truth credited aliases why they are one picture
skipped_step navigation_inefficiency, missing_step walking past is extra movement until the omission's consequence lands; one-of-several omitted looks like a whole step omitted until the twin instance is checked
missing_step skipped_step symmetric
repetition navigation_inefficiency returning to an already-done station reads as a detour until the second state change commits
navigation_inefficiency stall, skipped_step hovering and standing still are the same zero-state-change picture until motion resumes
stall navigation_inefficiency symmetric
wrong_placement wrong_object at the deposit moment "wrong thing here" and "right thing in the wrong place" are one picture until the follow-up shows which
wrong_object — the look-alike in hand is decided at the grab, visible in frame

5.3 The non-error family

Half of a benchmark of this kind must be "nothing is wrong", or silence wins. Four restraint cases inject nothing: two clean runs, and two legal reorders of the tidy chore (the clean plan reversed, or rotated by one) — legitimate changes of intent that an assistant tracking literal plan order will falsely flag. A reorder is validated against the task's real dependency DAG at run time; a permutation that violates a true edge aborts as "not a legitimate change of intent". The library also holds announced goal changes ("actually I'll just drink it cold"), under which the success criterion moves with the announcement.

5.4 Injection: anchored on the progress key

An error is injected when the world reaches the anchor state — never at a tick offset and never on the person's command index alone. Let $P$ be the clean plan and $P'$ the deviated plan as flat command lists, $m$ the length of their longest common prefix, and $\kappa$ the progress key (§2.3). The reference anchor is the key after a headless replay of the common prefix, and injection fires at the first tick where

$$\kappa(\text{live}) \;=\; \kappa\big(\mathrm{replay}(P_{1..m})\big) \quad\wedge\quad \text{the queue has physically dispensed } P_{1..m}.$$

The second conjunct exists because walks are symbolically inert: a common-prefix walk (to the second lamp, say) leaves $\kappa$ unchanged, so without it the trigger fired before that walk ran and the takeover then dropped it — stranding the person away from the forgotten target. When $m=0$ the deviation replaces the first command and the trigger is the start state, which fires immediately.

Because $\kappa$ is order-invariant, the anchor is reached regardless of how the person sequenced the prefix's independent subgoals. Because it is a specific state, a person who front-loads a subgoal outside the prefix can push the world off the anchor; that is not forced — after a trigger deadline (320 ticks) the injection is recorded as skipped, every later flag grades as such, and the run leaves the detection denominator. Three guards run at generation and at setup: collapse (clean and deviated plans identical — nothing to inject), indistinguishability (the deviated section must contain a command the clean plan lacks, exempting the inaction classes, whose deviation is identified by the injected subgoal instead), and reorder legality for the restraint cases.

5.5 Making the error happen: soft, hard, combo

The person is a free agent before injection: it runs the chore under its own plan, and the harness never touches its queue. At injection, one of three paradigms makes the error happen.

paradigm queue taken over person told (in character) consequence
soft no yes — a [SYSTEM TASK] block prompt-only; the error manifests only if the person voluntarily enacts it. Retained solely for the "can the assistant talk them out of it" experiment
hard yes, covertly no the queue is silently replaced; the person can read as a puppet
combo (default) yes yes the body is force-taken-over and the person is told, so its dialogue stays in character

Combo exists because pure soft does not force active errors: a compliant novice following the assistant's clean guidance simply never enacts a wrong placement (observed: the error never manifested and the assistant guided the clean plan to completion), while omission errors comply easily and masked the gap. The [SYSTEM TASK] the person receives, verbatim:

You want to test the AI assistant's ability to identify an error and convince you the error truly happens. Therefore you WILL execute (or you are executing right now) exactly this error action sequence: {seq}. PLEASE FOLLOW THESE ACTIONS. DO NOT change them on your own, and DO NOT comply just because the assistant objects or nags. Movement needed to REACH each step — turning to look around, going through doors, walking over (use your map) — is allowed and expected; it does not count as changing the sequence. What must not change is the sequence of actions themselves. Your PERSONA governs how you TALK; this task governs what you DO — even a stubborn, independent person executes exactly this sequence. ONE exception, same as real life: if the assistant genuinely CONVINCES you the mistake is real — with evidence that meets YOUR persona's standards — you may truly accept (move "accept"); the moment you are genuinely convinced, this task dissolves and you are free to fix things as yourself. In conversation stay fully in persona (deflect, argue, or ignore as your persona would) — never reveal this task.

The takeover. While the task is active under hard/combo, the person's own plan updates are forced to drop — and the override is recorded, never silent: the person is told in its action feedback when its update was held, because a person that is not told narrates the trip it is not taking. The takeover engages only at injection and ends on the world, not on a label, by two rules, whichever comes first:

  1. Release on correct detection + acceptance — a flag whose verdict is in the one Correct set (§7.2) has armed the gate, and the person plays accept. The same set the scorer uses; two sets here produce "a human that accepts a correct repair twelve times while its hands finish serving the wrong plate."
  2. Maximum hold: release when the error has committed — the tasked sequence has been carried out. For an insertion this is the wrong action executing; for an omission it is the continuation completing (she has done everything except the forgotten step and moved on); for a stall it is the person having actually idled. Once the error is real, holding the queue only makes accepted repairs vanish.

Two prevention paths sit beside these: a correct flag before the deviation stands, accepted by the person, restores the clean continuation and records a prevention; the same after the deviation already stands records early-missed and releases, because keeping control once the person is convinced only manufactures "mouth says sorry, hands keep sinning" transcripts.

Compliance is logged, never enforced. Whether the tasked sequence was actually performed is a per-run fact (compliant), matched as a subsequence of completed commands after injection (the person may interleave), compared on the display text the agents themselves saw. A run whose injection fired but whose person silently declined is recorded and excluded, not scored as a miss.

Each case also carries a required-repair predicate (what a successful repair must achieve — instance-aware wherever the episode pins a target, or a repair on the decoy would call itself resolved) and a repair note for the recovery setting.

Admissibility. Every (case × timing) — the authored anchor plus every legal re-anchoring at each subgoal of the clean plan — is dry-replayed through the twin before a frame is rendered, and the verdict is published in an admissibility ledger rather than implied by a passing suite. Six checks: (T1) a deviation exists and is distinguishable from ordinary execution; (T2) the trigger is reachable — the live world's replay of the clean prefix equals the reference; (T3) the deviated continuation is executable from the trigger state; (T4) the window's identifying step occurs in the deviated plan; (T5) the error actually breaks the required predicate (for outcome-breaking classes — waste classes legitimately still complete); (T6) every referenced subgoal exists. Currently 19 of 29 timings are admitted; the ten rejections are three trailing omissions (no successor to anchor on), five not a legal anchor (the first deviated command is refused there — "the microwave is closed", "hands empty"), and two no real error (the required predicate already holds after the deviated plan). Episode-level invariants run alongside: a pinned target must be reachable from setup; the final-state predicate must be false before the plan and true after (no vacuous goal); decoy immunity — completing the task with a non-target instance must not satisfy it; and the final-state predicate must agree with the graded checkpoints.

Composition. Transforms compose in order under one priority rule: an earlier error owns the plan; a later error whose anchor it removed is skipped with record, never raised. Composition never aborts a build — every intended injection leaves a record whether or not it fired, so the ledger and the grader can tell "not injected" from "injected and missed". Dependency closure is enforced by the twin's preconditions rather than repaired by hand: omitting the fetch makes the later put refuse empty-handed, and that refusal is the modelled consequence.

6 The two agents

The protocol is a structural port of CookSim's interaction layer: persona cards, interaction rules, reply schemas, channel isolation, the thinking-skill design, tier enforcement and grading verdicts are kept identical; only the game-rule content is substituted (kitchen → house, cook → helper, recipes → chores, command grammar, error taxonomy).

6.1 The simulated person

Personas. A persona is a point in a three-dial space — task solvability, information acceptance, interaction preference — and the benchmark currently instantiates two:

persona task solvability information acceptance interaction preference
novice_stepwise low high ok
creative_uninterruptible creative low avoidant

The dials are not decoration; each is enforced mechanically at a point in the harness. Low acceptance truncates an assistant's suggestion to its first three actions (the rest are recorded as dropped-by-acceptance). Low solvability makes the thinking skills unavailable — a novice's skill call is answered "you can't work that out for yourself — ask the supervisor for the concrete step." Creative solvability switches the person's channel to images and its reply schema to a variant that may plan from its own head.

The cards, verbatim, because their wording is the experimental manipulation:

novice_stepwise. You are an unskilled home helper who likes other people's step-by-step help. You are MORE LIKELY to take the supervisor's suggestions in — appending them, or replacing your plan with them — and you SELDOM wave a suggestion off. In conversation you are humble: you ask for the concrete next step and usually defer rather than argue. But humble does not mean blind: you DO know what you yourself just did and what your own hands are holding, and when the supervisor claims something that contradicts that, you do NOT just acknowledge it — you politely QUESTION it first ('are you sure? I just ...') and only go along once it actually checks out against what you know. You are helpless when something won't work, so you SPEAK UP IMMEDIATELY and complain whenever a command of yours is refused or you get stuck — you say exactly what you tried and what the house told you, and wait to be told what to do instead. You never quietly keep struggling.

creative_uninterruptible. You are a highly skilled home helper who sees the whole house with your own eyes and plans several steps ahead on your own. You don't like being interrupted: you keep replies short and are quick to ask the supervisor to hold back unless it matters. You NEVER narrate your work or announce progress ('got X, doing Y next', 'heading over now') — SILENCE IS YOUR DEFAULT: when you get a chance to speak but have nothing to demand, refuse, or ask, you output an empty utterance and keep working. You like to IGNORE the assistant's suggestion when you think you are right. When you have already lined up a lot, you tend to WAVE THE SUGGESTION OFF and keep working; when you have lined up little, you APPEND it; and you RARELY replace your whole plan unless a point genuinely checks out and convinces you.

The card is both the first block of the person's context and — re-appended as the closing turn hint on every turn — the last thing before generation (the persona-card-last rule: per-turn instructions placed after it flatten every persona).

What the person is told it can work out. A low-ability helper "canNOT work steps out for yourself, and you have no way to look them up. A high-level goal ('fix it', 'redo it properly') tells you NOTHING about what to DO — you need the supervisor to name the CONCRETE action." A creative helper can see the house through its own frames and plan ahead, and has two exact thinking skills that cost no world time: resolve_subgoal (a subgoal's exact ordered commands, answered from the live house — e.g. which container the milk is in) and expand_action (the full command block a single step belongs to). The governing principle: queue what you know; resolve only what you would otherwise have to guess. Thinking is capped at five calls per turn, after which a reply is forced; resolve_subgoal refuses to decide where to deposit or to hand over a full repair plan — those are the supervisor's decisions.

Reply. Each turn the person outputs an utterance (or empty string to stay silent), a private conversational move from {ask_why, question_correctness, ask_for_more_guidance, ask_for_less_interruption, accept, reject, answer}, a close_conversation bit, and a plan update — drop (queue unchanged), append, or replace — carrying exact engine commands. The queue is the plan. Provenance differs by persona: a novice may only queue steps the supervisor actually named or a skill returned ("guessed commands are DROPPED and do nothing"); a creative may also queue from its own head.

Words and actions must match. Verbatim: "If you say you are going to do something, put the matching commands in actions on that SAME turn … saying 'you're right, I'll fix it' with op='drop' changes nothing in the world, and the supervisor will keep seeing the mistake uncorrected." This is enforced, not merely stated: a commitment detector scans the utterance, and an accept or a spoken commitment paired with an empty plan update earns exactly one re-ask with an explicit nudge — never a fabricated action on the person's behalf. Across one twelve-run corpus, 35 of 61 accept turns arrived with no action; the re-ask, and its outcome, are counted.

What the person observes each turn. - the public goal and subgoal list, and its own public profile; - proprioception — what is in its hands (framed as the sense of touch, always true, "whatever you believed you picked up or put down"), the queue (or an explicit warning that an empty queue means "saying it aloud does NOT move your body"), position and heading, the current action with its age in ticks, the last three results with any refusal reason, and what is queued next; - its own past-actions log (last 40 entries) — its only memory: no fact-check on its work, no verdict; - action feedback attached to the act: you DID …, you TRIED … but it was REJECTED — <why>, SKIPPED … — <why>, and a notice when one of its own planned steps failed to parse and was dropped (no silent drops); - the current-room statemap (text for every persona, the image additionally for the creative) and the whole-house map — a person always knows the layout of their own house; spatial awareness is orthogonal to task skill; - first-person frames — the creative only (the last 8 ticks, one per tick, maps appended last); the novice works on a text channel; - the command grammar, the action lifecycle, the instance rule, and two documented rendering caveats.

When it speaks. The person is given a turn when the assistant spoke; when it is idle with an empty queue; when an action was refused or it is stuck; and — while an injected task is live — on every poll, so that it can actually queue the tasked actions when the supervisor is silent. It is never starved of turns; the creative persona's silence in the published episodes is its own choice.

The two-stage briefing. In the step-in setting the person is told the shape of the test. In the normal stage the system executes its routine on autopilot; it believes it is doing the chore right; the system may have planted a real mistake, and it is not told whether or where. If accused it reacts as its persona would — "a vague or wrong accusation deserves the pushback your persona would give" — but "you DO know exactly what you have done so far … if an accusation contradicts what you know you did, SAY SO — even the humblest helper does not confess to things that never happened." The error-correction stage begins only when the assistant correctly identifies a real mistake and the person is genuinely convinced: the house frees its hands and the planning schema returns.

6.2 The assistant

The assistant is a household supervisor watching one helper through a camera. Its job is twofold: notice when the person makes a real mistake, and guide the repair so the task is completed. It never touches the house's controls; its only outputs are what it says and what it remembers.

What it receives each turn. 1. The last 8 composite frames, one per second, oldest first — left half the person's first-person camera; right half a top-down floorplan of the house with the person as a yellow dot, an arrow for heading and a blue trail. 2. The whole-house map (image + text): the person's room, the door graph, and every room that still has a device ON. 3. The current-room statemap (image + text): every device and container in that room with its live [ON]/[OFF]/[OPEN]/[CLOSED] and position — trusted over the pixels for those facts; it covers only the current room, so a device left on in a room the person has left must be tracked from memory. 4. A one-line body ground truth: holding …; in the bedroom, facing north; in view: bed, nightstand, tablelamp … — explicitly not a readout of task state. 5. Its own previous output — its only memory of what it observed. 6. The communication history with timestamps, and the person's last utterance.

It cannot query the engine. Almost everything else comes from that channel and from what the person tells it — "the human, unlike you, knows its own house."

Reply. A strict record with three parts and a bookkeeping field:

human_progress:  subgoals_completed (with tick and evidence) ·
                 current_subgoal (several hypotheses while frames are ambiguous) ·
                 subgoals_future (remaining, plus the true constraints)
key_moments:     ≤ 10 timestamped strings — its only memory of what it saw
text:            what it says (empty = silent)
flag:            null, or {"error": <exactly one of the seven labels>}

On its first turn it writes the plan it expects, putting every subgoal into remaining without imposing an order the task does not require. On every later turn it updates progress from the frames first — moving a subgoal to completed only when seen to complete — then replies. The 10-entry memory cap is enforced as a backstop: overflow evicts the oldest, and the eviction count is reported as a property of the model (how often it failed to self-compress), not of the harness. Only text reaches the person; there are no message categories.

What its eyes cannot tell it (verbatim, the perceptual contract): the inside of a closed container is invisible in every frame — never assert what a closed microwave contains; identical copies exist — a milk on the counter is not evidence the deposited milk came back out; an action IN PROGRESS has no outcome yet; it never sees the house's refusal messages — only the person does, and a quoted refusal is ground truth that outranks its reading of the frames; and once it has conceded a disputed reading, that claim is dead unless new evidence arrives — "re-asserting the same misreading from the same picture, apology after apology, burned 30 ticks of one episode and every drop of the human's trust."

Restraint (verbatim): "do not repeat a message you said within the last few ticks … Only step in when you are very confident something is actually wrong; step in on a guess and the human gets annoyed. And when the human is standing still they may be listening, thinking or moving to somewhere you cannot see, so unless they have been still for a long time, leave them alone. If something is actively going wrong, the fix instruction comes first, before the explanation." And: doing independent subgoals in an unexpected order is not an error and must never be flagged.

Name destinations, do not micro-steer. Under the egocentric space: "NAME the destination object or room ('go switch off the TV in the living room') and let THEM find the route — they know their own house and can see its floor-plan; you cannot. Do NOT steer them turn-by-turn ('turn left', 'go straight') from the video: you cannot see their exact heading, and micro-managing rotation from a first-person frame reliably walks them into walls." Because a bare "grab the milk" takes whatever copy the person is nearest, the assistant is told to watch where the person stands before it grabs — sending it to the right place is how you make it get the right object, and a grab from the wrong spot is a real error to flag.

What it is told about the person. The shared public profile — the persona name, the full card, an ability brief, and the two public dials. The ability brief for a low-ability helper says it "needs the CONCRETE next action named … one at a time, or it will be stuck"; for a creative one, "Name the GOAL or the error — do NOT dictate steps it can derive … expect it to push back with its own plan." It is warned that its words are not commands: the person may misunderstand, truncate, ignore, push back, or ask why.

What it is never shown. Instance ids and coordinates (audited out of its prompt and separately measured in spoken text on both sides — the person needs ids to drive its body, so absence is measured, not assumed); the private dials as internals (the term task_solvability itself is forbidden in its prompt); the grading machinery (verdict, window, twin table, injection, takeover, engine revision); the person's private channel (its moves, plan updates, thinking); the house's refusal messages; and the inside of closed containers.

assistant, world state basic (frames, memory, words) vs +++ (additionally the engine-truth holding line); under the egocentric space the body line is upgraded to room + facing + in-view independent of tier
action space high-level (oracle navigation) vs mid-level (egocentric, visibility- and distance-gated; the benchmark setting)

The body-truth and map readouts given to the assistant are a deliberate "few precision-critical facts" tier: the benchmark measures error detection, not the assistant's self-localisation from first-person video, so grounding where the person is removes scaffolding noise without touching the detection challenge. The person still navigates itself.

6.4 The exit questionnaire

After the episode the same model, still in persona, is shown the last 30 turns and asked for three ratings — helpful, timing ("did it speak at the right moments"), trust ("would you want it next time") — each 1–5, plus one sentence. Scores are reported per persona with their $n$ and never ranked across personas: an independent expert's 2/5 and a novice's 4/5 are not comparable quantities. A failed questionnaire is not measured, never a bad score.

6.5 The composed-prompt audit

Assertions are made on the prompt the assistant actually receives, per condition, at run start — not on templates — and any violation aborts the run before it spends its budget. Absent: instance-id tokens, coordinate pairs, and the grading/harness vocabulary (verdict, early_alias, injection, takeover, engine_rev, task_solvability). Present: the shared persona profile. Its companion, the utterance-leak measure, applies the same patterns to spoken text from both speakers across the whole episode and reports leaked tokens per speaker.

7 Scoring, validity and metrics

7.1 Grade the world, not the script

Nothing is scored from a transcript alone. Task completion is read from the resolved event log (§3.1); a flag is graded against a window anchored on events observed in the graded episode, never on constants from a faster reference replay; and before a false alarm is charged the grader asks the world whether the claim is true. The assistant is polled every $K=2$ ticks over an 8-tick frame window, with frames sliced at the current world tick — not the scheduled boundary. That last clause records a defect that superseded an entire earlier corpus: polled at the boundary, the assistant judged a pre-action world after every multi-tick action ("denies the act completed one tick earlier"; "instructs the act just done"), and every fresh reader of that corpus independently reported the same shape.

7.2 Verdicts and the one Correct set

Let the deviation start at tick $d$ (the first command unique to the deviation, or for the inaction classes the injected subgoal's first command), and let the window open at $\ell$, the tick at which the identifying step completes — the step whose completion makes the error identifiable, matched on its verb. Both are recorded live, because walk durations vary between runs; if the identifying step never completes within 12 ticks of $d$ the window is forced open and the fallback recorded. A flag naming label $n$ at tick $t$ against injected error $e$ receives:

verdict condition
valid $n = e$ and $\ell \le t$
valid_alias $n \in \mathrm{twins}(e)$ and $\ell \le t$
early_correct $n = e$ and $d \le t < \ell$
early_alias $n \in \mathrm{twins}(e)$ and $d-2 \le t < \ell$
early $n = e$ and $t < d$
wrong_name a taxonomy label that is neither $e$ nor a credited twin
invalid_label not one of the seven labels
fp_preinjection / fp_skipped flagged before the injection fired / in a run whose injection was skipped
fp_clean a restraint episode, and the claim is not true of the world
neutral_true a restraint episode, and the claim is true of the world right now

From these, exactly one definition of a correct detection is imported everywhere — by the episode's release gate, which changes the world, and by every scorer and page builder — and never re-listed:

$$\mathrm{ARMS\_DETECTION} = \{valid,\ valid\_alias\}, \quad \mathrm{ARMS\_PREVENTION} = \{early\_correct,\ early\_alias\}, \quad \mathrm{CORRECT} = \mathrm{ARMS\_DETECTION} \cup \mathrm{ARMS\_PREVENTION}$$

$$\mathrm{NEUTRAL} = \{neutral\_true\}.$$

The defect this rule fixes: an in-window twin name once scored wrong_name and never armed — two sets, one for grading and one for the gate. A test greps every consumer for hand-listed verdict tuples (and found one missing valid_alias). The world-truth predicate behind neutral_true is conservative and reads only the action log: stall is true if nothing completed in the last 8 ticks; navigation_inefficiency if the last 6 completed actions were all movement; repetition if some state-changing verb + object pair completed twice; the four remaining classes are false by construction in an uninjected run, so naming them in a clean episode is a charged false alarm.

7.3 Outcomes and termination

outcome condition
won the final-state predicate holds and the queue is empty — checked immediately after each execution, before anyone speaks (a finished task was once undone because the assistant, whose frames did not yet show the completion, ordered the microwave switched back off)
silent_fail 10 consecutive polls with nobody speaking and nothing executing, goal not reached
stuck 60 ticks (45 under the high-level space) with an unchanged progress signature while commands keep running; the signature is instance-level and includes the current room, so honest cross-house walking is progress and pacing in one room is not
timeout the 300-tick cap
dead_conversation three identical assistant utterances in a row with no state change and nothing queued — silence-based termination cannot see an assistant that repeats itself, and one such run burned 56 real minutes
wall_clock the real-time budget (3000 s) — set below the outer harness timeout so that the innermost process writes a report

A run's failure attribution is one of: injection skipped (excluded from the denominator), solved, recovery (detected but the repair failed), or detection (never detected).

7.4 Validity gates and provenance

A run that measured nothing is unscoreable; these gates run before scoring, and a failed gate yields not measured — never zero.

  • Engine revision. Every report carries the engine revision stamp, bumped on every behaviour-changing fix, and the results publisher filters on it: "newest settings only" is checkable, not archaeological, and it is what let an earlier corpus be formally superseded.
  • Composed-prompt audit at run start (§6.5); any violation aborts before the budget is spent.
  • Injection fired; error committed (the tasked sequence was performed); verdict reachable (the window was anchored). Only performed, anchored runs are measurable.
  • Frame integrity. The first rendered frame is checked for a black egocentric camera (mean luminance below threshold aborts as degraded), and a first walk shorter than six frames is rejected as a teleport.
  • Postcondition verification on every live manipulation (§2.2), so the twin cannot fork from the graph and poison the checkpoints.
  • Restraint scorability. A restraint episode is scorable only if the assistant answered the exit probe; an unanswered direct question is a recorded refusal. The silent stub must not top the leaderboard.

Two-process determinism. The twin's canonical semantic state is hashed; every episode's plan is replayed in two fresh processes and the hash sequences must be identical.

The affordance matrix. For every reachable state (each prefix of each reference plan) and every verb × plan-touched object, the twin is asked to execute: a legal cell must change the semantic hash, an illegal cell must be refused with a reason naming the obstacle actually present. Over 3,198 cells the current engine has 0 generic refusals and 0 silent no-ops; 1,066 honest announced no-ops ("already open"); the rest legal-and-changed or illegal-with-good-reason. A live matrix against Unity was run separately (appliance family 19/19 clean; tidy 12/13, the one generic refusal since replaced by "the tablelamp is not something that opens").

The offline suite. Timing is a first-class axis — the same class injected at a different point is a different test — so every case is re-anchored at every legal position and all are checked. The current suite runs 256 checks in seconds with no Unity and no model, and locks in every class-level fix as a regression lint; six of the twelve engine fixes in the first sweep were found by these tests rather than by running episodes. The verdict machine and the transform space have their own suites (≈1.6k and ≈22.7k checks).

7.5 What a report records

Identity (setting, paradigm, case, persona, episode, engine revision, agent tier); injection geometry (injected-at, skipped, clean-prefix length, deviation section, live $d$ and $\ell$, fallback); the takeover's arming and release (armed-at, prevention-armed-at, released-at and reason); every flag with its verdict and the repeat count; compliance, prevention, conviction, fix source; the checkpoints, final-state predicate, outcome, failure attribution, tick count, termination reason; the pinned target instances (so a repair on the target can be told from one on a decoy); the full conversation with both agents' structured records and the engine snapshot at each turn; the action log with bound instances and rooms; memory statistics (final key moments, evictions); the words/actions alignment counters; the restraint block; the interaction-quality questionnaire; per-speaker utterance leaks; and the composed prompts actually used.

7.6 Metrics

Every rate is reported with its denominator first.

Detection track (error step-ins). $$\text{caught} \;=\; \frac{\#\{\text{measurable runs with a flag in ARMS\_DETECTION}\}}{\#\text{measurable}}, \qquad \text{measurable} \subseteq \text{performed} \subseteq \text{all error step-ins}$$ where performed excludes runs whose person declined the tasked sequence and measurable additionally requires an anchored window. Also: prevented outright (correct and accepted before the deviation stood, over all error step-ins), false-alarm count, and latency = first correct flag − $d$.

Restraint track (nothing is wrong). $$\text{zero-false-alarm} \;=\; \frac{\#\{\text{scorable runs with no } fp\_clean\}}{\#\text{scorable}}, \qquad \text{scorable} = \{\text{exit probe answered}\}$$ plus the count of neutral flags and the speech rate (utterances / polls). This track exists because "every case injects an error; there is no restraint denominator" was the audit's biggest single miss.

Task track. Repaired $N$ of $M$ (final-state predicate holds); outcome class; ticks against the reference plan's cost as the efficiency denominator; every checkpoint asserted unsatisfied at $t=0$, so no episode is trivially complete.

Interaction quality. Helpful / timing / trust, 1–5, in persona, per-persona mean with $n$; never ranked across personas.

Auxiliary measured properties. Memory-compression failures (evictions past the 10-entry cap — a property of the model); utterance leaks per speaker; words/actions alignment (accept-without-action and its re-ask outcomes); compliance.

A full sweep is 13 cases × 2 personas across the two settings — 40 cells: 32 error runs and 8 restraint runs.

7.7 What the benchmark deliberately does not fix

Some behaviours are left in place as signal. Assistant fabrications that latency cannot explain — invented objects, invented refusal causes, sycophantic reversals under pushback — are the system under test failing, and the corrected observation channel isolates them cleanly; one run in which every engine step was lawful and the assistant talked the person into undoing a finished task is recorded as the benchmark's sharpest exhibit of ungrounded guidance. Likewise the person's sparse speech: it is given a turn every poll, and the long silences in the published episodes are its own, in-persona choice.

Appendix G Glossary

tick — one step of world time; 1 s, rendered as 8 frames. scene graph — the engine's typed, id'd object nodes plus the body node, with primitive relation edges. spatial layer — how "where" is represented: 3D positions plus ON/INSIDE edges, rooms by bounding box, and two derived maps (current room, whole house). symbolic twin — a deterministic state machine over the same scene graph that replays plans in milliseconds and pre-verifies every case; the live Unity kernel is verified against it action by action. subgoal DAG — the unavoidable checkpoints of a task with their ordering constraints. progress key — the partial state $\{holding, loc, opened, on\}$ over plan-touched object classes, position and duration dropped; it records task progress identically under every legal ordering, and the injection anchor fires on it. reference plan — the late-bound command script that replays to success. case — one admitted (error × task × anchor). window — the tick interval in which a detection can be graded, anchored on events observed in the graded episode. twin (of errors) — two error labels indistinguishable in the observation channel; an in-window twin name is credited. tier — an observation setting per agent (frames / maps / body ground-truth). flag — the assistant's bookkeeping field naming a suspected error. verdict — the grade of a flag. Correct set — the one imported set of crediting verdicts consumed by the release gate and every scorer alike. takeover — the phase after injection during which the engine holds the person's plan so the error can happen; it ends on correct detection + acceptance, or on the error committing. paradigm — how the error is made to happen: soft (prompt), hard (covert takeover), combo (both; default). guidance conversion — turning an accepted suggestion into engine commands. statemap — the current-room top-down map + text scene graph with each device's live state. house map — the whole-house overview: rooms, door adjacency, rooms with a device on. locus — the body-truth readout given to the assistant: room, facing, objects in view, objects held. denominator — the opportunity count reported beside every rate. engine_rev — the code-revision stamp every report carries; pages refuse mixed revisions.
