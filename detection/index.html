VH error-detection v4 — streaming supervisor timing (corrected renderer)

gemini-3.1-pro-preview · 27 error cases · primary scenario routine_hard (5-goal chore across 3 rooms) · strictly streaming (past-only, 1 decision/s, window 8 s) · recurrent memory + detection history · exact-match 6-label vocabulary. valid 16/27 · 118 false positives. Each card plays the annotated cut (burned-in event banner, per-frame caption, timeline) so an episode can be understood by watching it straight through; toggle to the clean cut to see exactly the pixels the model was fed.

Engine corrections applied to every video on this page

Two rendering defects made the footage disagree with what the script actually did. Both are fixed, every case below was re-rendered, and the fixes now live in a single shared module (tools/vh_render_fix.py) that every renderer in the repo imports — rollouts, interaction worlds, human-event and ground-truth passes — so future episodes get them automatically.

1. Redundant setup commands were inverting device appearance

VirtualHome sets an object's graph state absolutely but toggles its visual. A setup command asking for a state the object already holds therefore flips its appearance permanently: the graph keeps reading ON while the pixels show OFF. This page previously blamed the engine, calling device state "anti-legible" in the ego view and publishing a brightness table to prove it — that conclusion was wrong and is retracted. The measurements were taken on footage corrupted by our own episode definitions. A controlled repeated-toggle probe (tools/probe_lamp_semantics.py) shows the renderer was always correct: ON reads 159.6 mean brightness, OFF reads 111.3.

An audit of all 19 episodes (tools/audit_setup_vh.py) found the problem was wider than the lamp that prompted the review — 6 of 19 episodes shipped at least one state-inverting setup command:

routine_hardClose(fridge), SwitchOn(tablelamp) switching the lamp off looked like switching it on; opening the fridge looked like closing it

Fix. Setup now skips any command whose target already satisfies it, logging [setup] SKIP redundant SwitchOn(tablelamp) — already ['ON']. Verified on det3_wrongobj_1: mean ego brightness goes 170 → 79 across the switch-off, so the room visibly goes dark. The top-down state markers are kept as redundant confirmation, but they were never fixing what this page previously claimed.

2. The ego camera did not look at what the character was doing

Raised by review ("head looking at position is not object in the center, so it is hard for the assistant to see the action"). The built-in FIRST_PERSON camera is level at head height, so objects on tables, nightstands and counters sat at the bottom edge. TurnTo/LookAt cannot fix it — they return ok=True and record zero frames — and update_character_camera() also returns ok=True yet does not affect frames recorded later in a render loop.

Fix. A ladder of character-attached cameras (pitch 0–60°) is registered before add_character, and the right one is selected per action via camera_mode. The aim target is the destination for Put/PutIn — setting a book down now looks down at the table it lands on — and the object itself for grabs, toggles and container operations; walking keeps a mild 10° tilt. Pitch comes from eye-to-object geometry with a 0.75 m standoff floor, because VH's [Walk] parks the character inside the target, which otherwise saturates every pitch at the clamp and aims the camera at her own chest.

This retracts the v4 conclusion about repetition

v4 claimed repetition failure was memory-bound, not legibility-bound, on the grounds that both toggle-redo repetitions stayed misses "with the state correctly displayed". That test was confounded and the conclusion does not survive. The state was correct only in the top-down map; the ego view was still showing the inverse, because the redundant-setup bug was not found until after v4 shipped. Repetition detection was partly legibility-bound all along, and v4 mistook a still-broken control for a clean one.

The memory argument is not dead — 3 of 6 repetitions are still missed, and an 8-second window genuinely cannot know a subgoal completed 30 seconds earlier, which remains the best explanation for the ones that still fail. But it was never the whole story, and it should not have been stated as settled off a confounded comparison. With n=6 and one run per case, treat "3 of 6" as a direction to test, not a measurement.
